# Design

## Context

See `proposal.md` for motivation and `specs/exactly-once-semantics/spec.md` for the behavioral contract. The repository currently has one Docker Compose file, a single-node Kafka KRaft broker, an empty `cnc-demo-records` topic, a registered canonical JSON Schema extracted from `DATA.md`, and Python schema/Compose/smoke tests. There is no Java build, consumer, producer, or database. Existing base checks (`tests/test_compose_contract.py`, `scripts/smoke_check.py`) explicitly reject application services and require an empty sample topic. Their no-application assertions are obsolete for the expanded default stack; retain the empty sample topic and broker/registry health assertions while adapting service checks. The published base capability's former no-application scope also needs amendment to describe this later feature.

## Goals / Non-Goals

**Goals:**
- Keep the existing infrastructure and empty canonical sample topic verifiable while the cut comparison runs as part of default startup.
- Demonstrate Kafka atomic output-plus-offset commits and, separately, PostgreSQL event-ID idempotence; expose their different failure boundaries.
- Preserve existing volumes and base schema on normal stop/restart.

**Non-Goals:**
- Distributed transactions between Kafka and PostgreSQL, or exactly-once row insertion in the transactional Kafka path.
- Kafka Streams transformations, predictions, fault injection in generated telemetry, assessment/event generation, new domain fields, or replacing base broker/monitoring infrastructure.

## Decisions

### 1. Extend the default Compose stack

Add PostgreSQL, cut-topic/table and schema initialization, the four Java producer/consumer services, and metrics collection to ordinary `docker compose up`; no profiles, alternate modes, or separate startup path. Gate application startup on broker, Schema Registry, topic/schema setup, and PostgreSQL readiness. Use `--if-not-exists` topic creation and `CREATE TABLE IF NOT EXISTS` for non-destructive restarts, and never publish to or rename `cnc-demo-records`. Replace only obsolete no-application checks in the base test/smoke suite; retain its sample-topic/schema, broker/registry health, and UI assertions and extend it to check readiness of new services. The baseline spec's scope restrictions reflect the earlier bootstrap milestone rather than a permanent limitation and require a corresponding requirements amendment. Alternative: an opt-in profile would preserve the old no-app condition but contradict the requested one-command startup.

### 2. Use one small Java 21 application/build with two producers and two consumers

A Maven build (new scaffolding, no Java build exists) packages two producer roles and two consumer roles behind four distinct Compose services. Each consumer reads its paired producer's source topic and writes directly to its own PostgreSQL table; the first consumer additionally emits the processed-cut Kafka topic transactionally. Share record generation/serialization and JDBC plumbing without adding a third consuming service. Set the Maven `groupId` and base Java package to `com.improving.gotogether`; place application and test classes under `src/main/java/com/improving/gotogether/` and `src/test/java/com/improving/gotogether/`, with cut-domain subpackages as needed. Use Kafka Java clients for explicit producer transactions and offset commits, pinned Avro and Schema Registry serializers/deserializers for Kafka values, and PostgreSQL JDBC; use JSON only for the canonical-contract checks and the decoded database projection, never as the cut-topic value encoding. Pin vetted versions at implementation time. Alternatives: Kafka Streams EOS (more implicit transaction boundaries for this comparison), or multiple builds (needless duplicated setup). Give all topics, groups, client IDs, tables, services and classes cut-domain names, such as `mill-cuts-transactional-source`, `mill-cuts-committed`, `mill-cuts-replay-source`, `mill_cuts_transactional_writes`, and `mill_cuts_idempotent_writes`, rather than naming domain objects after this change or its guarantees alone.

### 3. Generate identical canonical cuts independently

Both producers use the same pure function of cut index, a fixed UTC starting instant, `mill-1`, a stable cutter ID, and the cut measurement fields in `DATA.md`. Default to a finite run of 30 records spaced two seconds apart; share run length and interval via Compose configuration. Use deterministic nonnegative illustrative measurement values and stable `event_id`s; no new JSON fields, fault labels, or external data. Validate normalized decoded samples with the existing `schemas/cnc-demo-records.schema.json` and `jsonschema` format checking in tests; compare decoded canonical values rather than Kafka bytes, because each topic uses its own Schema Registry value subject and may have a different schema ID. The transactional-source producer uses `enable.idempotence=true`, acknowledgments from all in-sync replicas, and retries; the replay-source producer uses `enable.idempotence=false`, retries, and acknowledgments for at-least-once delivery. Stable IDs survive process restarts; Kafka producer idempotence protects retries within a producer session, not arbitrary new sessions or re-runs. For a fresh run compare the ordered source sequences; on persisted restarts compare logical event IDs rather than asserting Kafka has no duplicate records. Keep the finite producers alive but idle after completion until demo shutdown so their metrics targets remain scrapeable and a zero rate is not confused with a missing target. Alternative: one producer fan-out to two topics, rejected because two independent producer configurations are required.

### 4. Derive a cut-only Avro contract and register topic values

Generate a checked-in Avro record schema deterministically from the `cut` branch and common envelope of the JSON Schema embedded in `DATA.md`; verify regeneration against the asset in static tests, rather than treating a hand-authored second schema as authoritative. Preserve `schema_version`, `event_id`, `kind`, `occurred_at`, `machine_id`, `tool_instance_id`, and nested `payload` with `cut_index`, `vibration_rms_g`, `spindle_current_a`, and `coolant_flow_l_min`. Use namespace `com.improving.gotogether.cuts`, Avro string for the existing RFC 3339 timestamp and IDs/constants, `int` for the demo cut index, and `double` for measurements; do not add metadata or new domain fields. Avro cannot express JSON Schema `const`, `minLength`, nonnegative numeric bounds, or date-time format, so check these on generated values before publish and on decoded values before processing or database persistence (including the valid `int` range). Create/verify `<topic>-value` subjects with schema type `AVRO` for `mill-cuts-transactional-source`, `mill-cuts-replay-source`, and `mill-cuts-committed` in a default-startup registry setup job; on mismatch fail without replacing or incrementing a version. Keep `cnc-demo-records-value` as the unchanged base JSON Schema subject. Use Schema Registry's Confluent Avro framing (magic byte plus schema ID) and subject-aware serializers/deserializers for all three topics; reserialize the first consumer's Kafka output for the committed topic rather than copying source bytes with a source-topic schema ID. Alternative: raw Avro bytes without registry IDs (rejected for this demo's discoverable per-topic contracts), or replacing the base JSON subject (breaks the base contract).

### 5. Make the first consumer's Kafka transaction visible

The first consumer reads only `mill-cuts-transactional-source` with auto-commit disabled, produces the validated cut to `mill-cuts-committed` with a stable, unique `transactional.id`, writes the same cut directly to `mill_cuts_transactional_writes` and commits that database write, then calls `sendOffsetsToTransaction` with current group metadata and commits the Kafka transaction. On database failure, abort Kafka output and do not commit the source offset; on rebalance or failure before Kafka commit, abort/rewind and retry. This order prevents an acknowledged source offset from skipping an unwritten database row, but a crash after the PostgreSQL commit and before Kafka commit can duplicate that row on replay. Use one partition per topic for unambiguous order and `read_committed` for observers of the processed topic; no third application consumer reads it. Broker transaction-log replication/min ISR are already set to 1 for the single-node demo. Cover the DB-commit/Kafka-commit ordering and replay boundary with focused unit tests rather than a runtime crash-injection harness. Alternative: commit Kafka before PostgreSQL (can lose a database write permanently), or add a separate processed-topic sink (violates the two-consumer topology).

### 6. Deliberately contrast two database persistence modes

Expose PostgreSQL only on host loopback (configurable host port) and the Compose network; provide local demo-only credentials via external environment configuration, never commit actual secrets. Initialize two tables with the canonical cut ID and a JSON/JSONB projection of the validated, decoded Avro cut value (plus operational metadata if needed); Kafka values themselves remain Avro. `mill_cuts_transactional_writes` has a surrogate row key and intentionally no uniqueness constraint on `event_id`; the first consumer writes directly to it from `mill-cuts-transactional-source` as part of its processing loop, before committing the Kafka output/offset transaction. `mill_cuts_idempotent_writes` uses `event_id` as its primary key; the second consumer reads only `mill-cuts-replay-source` in its own group and uses `INSERT ... ON CONFLICT (event_id) DO UPDATE` to replace the stored canonical cut fields with the later delivered values. An identical redelivery leaves one equivalent row, while a changed value with the same ID overwrites that row; this is last-delivery-wins by event ID, not detection of conflicting IDs. Both consumers disable auto-commit and retry without offset advancement on database failure. Check write-before-offset and primary-key upsert behavior with focused unit tests; do not add an integration-only crash hook. Kafka transactions do not include PostgreSQL, so duplicates in the first table are intentionally permitted. Alternative: adding an `event_id` primary key to the first table hides the contrast and implies a stronger database guarantee than that path actually demonstrates.

### 7. Extend the existing Prometheus and Grafana deployment

Add scrape jobs for each of the four Java producer/consumer services to the current Prometheus configuration while preserving the broker and registry targets. Export bounded cut-specific metrics using the repository's checksum-verified JMX exporter approach: producer sends and send failures by producer client ID; consumer processed records and processing/transaction/database failures by group ID. Add a pinned Kafka consumer-group lag exporter running by default, reading group offsets versus source-topic end offsets for the first and second consumer groups; do not infer lag from broker-wide throughput, and label each group/topic distinctly. Use the existing Prometheus datasource and append cut panels to the provisioned `base-streaming-platform` Grafana dashboard, retaining its UID, broker/registry panels, and target-health indicators. Rates and lag must differentiate healthy idle/caught-up components from `No data` and unavailable scrape targets; use a rate window appropriate for the finite 30-record run. An application exception or rejected database write increments the affected role's error counter even when a retry later succeeds. Alternatives: broker JMX alone (no reliable per-group lag/application errors), or a separate Prometheus/datasource/dashboard (contrary to the unified operator view).

### 8. Keep verification proportional to the local demo

Update static Compose/monitoring tests to reflect default application/database services, retaining checks for the empty canonical sample topic, JSON Schema, broker/registry configuration, and the existing dashboard. Use focused Java/Python unit tests for deterministic cuts, Avro mapping, schema registration decisions, transaction/offset call ordering, replay-safe database writes, and metric labeling. Extend the existing startup smoke check rather than building a separate end-to-end or fault-injection harness: verify Compose service readiness, inspect logs for unhandled startup errors, and confirm host/Compose-network reachability of Kafka, Schema Registry, PostgreSQL, AKHQ, Prometheus, Grafana, and the expected topics. The smoke check should confirm the dashboard loads and monitoring targets are reachable, not exhaustively compare records, offsets, rows, or failure windows. Tests that start/stop Docker require user permission before running. Document ordinary Compose commands, endpoints, topic/group/table names, sample SQL, the existing dashboard, and Kafka-only versus database idempotence. Alternative: a multi-probe failure-injection suite would cost more than this local demonstration needs.

## Risks / Trade-offs

- [Kafka-only transactional scope is easy to mistake for PostgreSQL exactly-once] → State boundary in docs/tests and demonstrate duplicate allowance on the first table.
- [Producer crash/new session can duplicate a logical cut] → Stable event IDs, finite deterministic replay, and compare logical IDs separately from physical Kafka records; do not promise cross-session source deduplication.
- [Kafka transaction fencing/rebalances can stall processing] → Stable transactional ID, abort on assignment change, retry with backoff, and verify restart behavior.
- [Avro type checks alone admit invalid canonical values, and schema changes can drift from `DATA.md`] → Derive the cut schema reproducibly and validate semantic constraints before publish and after decode; reject mismatched registered subjects without rewriting them.
- [Old base-only checks and published scope conflict with expanded default startup] → Update service-scope assertions and amend the earlier base capability requirement, while retaining empty sample-topic/schema and broker/registry health coverage.
- [Finite low-rate sources produce sparse throughput series, and exited services look like missing telemetry] → Keep producers scrapeable in idle mode, display target availability, and use a rate window appropriate for the documented 30-cut run.
- [Lag exporter or app metrics collection fails independently of a healthy broker] → Display cut target health alongside lag/rates and test a missing target instead of replacing absent samples with zero.
- [Single-node broker/DB and local unauthenticated UIs are not production durability/security] → Limit host ports to loopback, document disposable data and avoid production claims.
- [Destructive reset erases shared Kafka and PostgreSQL demo data] → Use normal Compose stop by default; seek explicit approval before volume deletion.

## Migration Plan

1. Update legacy no-application requirements and assertions as part of the feature's documented contract, then add static tests before extending default Compose services, topics, database scaffolding, monitoring, and Java roles in small increments.
2. Verify focused static/unit checks; with user permission, run the single expanded startup smoke check against ordinary Compose startup, inspect service logs, and confirm endpoints and the existing dashboard are reachable.
3. Roll back by stopping the stack and reverting the added services and dashboard/scrape changes while preserving volumes unless the user explicitly authorizes disposal. Never reset the shared Kafka volume to roll back this feature automatically.
