# Design

## Context

See `proposal.md` for motivation and the three delta specs for observable behavior. The base dashboard currently has an empty `templating.list` and combines fixed producer and consumer identities in four time-series panels. Producer telemetry exposes `client_id`; consumer counters expose `group_id`; consumer lag exposes both `group_id` and `topic`. `metrics-that-matter.json` is generated by deep-copying the base dashboard and appending three outcome panels, and the current contract verifies that the baseline panels remain an exact prefix. Preserve that derivation model and the existing Prometheus collection sources.

## Goals / Non-Goals

**Goals:** Make dashboard selectors reflect labels actually available in the metrics; keep panel queries, units, and status states understandable; preserve deterministic parity of shared panels through the existing derivation and test pattern.

**Non-Goals:** Change metric meaning, Kafka or database processing, topic retention, collector architecture, Grafana/Prometheus deployment, authentication, or introduce a new dashboard plugin or data source.

## Decisions

### 1. Use Grafana dashboard variables that follow existing metric labels

Define producer-client and consumer-group variables from the corresponding Prometheus label sets, with an All value selected by default. Apply the producer variable to both producer throughput and error queries, and the group variable to consumer throughput, error, and lag queries. Define a topic variable from the lag series and apply it only to topic-labeled panels. Retain multi-series visibility for All, and use regex-safe variable formatting for selectors. Producer counters currently have `client_id` but not `topic`, so do not pretend that a topic selector filters producer series; producer client IDs remain the direct producer filter.

*Alternative:* Add topic labels to application counters solely to make every selector affect every panel. Rejected for this change: each producer's existing client ID already identifies its pipeline, while topic filtering is available on lag telemetry; changing metric schemas adds cardinality and migration work without being required by the explicit per-panel selectors.

### 2. Separate signals and map visualizations to the data

Create independent time-series panels for throughput and errors, and for consumer lag; aggregate by identity labels so selecting All gives a small number of readable series rather than partition-level clutter where aggregation is valid. Keep consistent rate windows, units, legends, and descriptions across corresponding pipelines. Use Grafana stat panels for retained DLQ length and unreconciled-row count, retaining their independent Kafka and PostgreSQL health series/availability semantics. Keep average staleness as a seconds-based time series because it changes over time. Represent each component's target health with an individual status panel and explicit value mappings/thresholds: healthy green, unhealthy red, and no data/unavailable as a distinct neutral state.

*Alternative:* Keep throughput, errors, and lag in combined charts, or render queue counts as time series. Rejected: the signals have different units and operational meanings; separate panels are easier to scan, while stat panels make current counts immediately legible.

### 3. Reorganize into operational sections and preserve dashboard derivation

Arrange panels in a consistent top-to-bottom operational reading order: broker/registry overview and health, producer activity, consumer activity/lag, component health, then event outcomes on the improved dashboard. Use uniform sizing for related panels, reserve wider panels for time-series graphs, and retain concise descriptions for non-obvious metrics. Grafana's official dashboard guidance supports reusable variables and panel descriptions; its time-series visualization is intended for measurements changing over time. Continue to generate the improved dashboard by copying the complete updated baseline (including its variables) and adding only the three outcome panels. Do not hand-diverge shared panels or variables between dashboard JSON files.

*Alternative:* Maintain the two dashboards independently. Rejected: duplicated edits can drift, while the current derivation script and parity tests already make the base dashboard the source of truth for shared content.

### 4. Extend contract tests around behavior and parity

Extend monitoring contract coverage to check the variable query labels, default All behavior, selector application to related queries, distinct panel types/units, per-component health mapping and unavailable state, and the intended query sources for outcome panels. Keep the derivation equality test and assert that every shared panel and selector is identical while only the improved dashboard contains the three outcome panels. Validate metric label availability against `monitoring/cut-app-jmx.yml` and the lag exporter contract. These checks provide a deterministic alternative to relying on a live Grafana session for basic dashboard structure.

*Alternative:* Verify only JSON parseability or visually inspect a running container. Rejected as the sole check: valid JSON can still have broken selectors, wrong metric labels, or dashboards that silently diverge.

## Risks / Trade-offs

- [All-value selectors could create clutter or include series without recent samples] → Aggregate queries by the selected identity and validate that empty/missing metrics remain no-data rather than healthy zero.
- [Prometheus label sets may be empty before finite producers have emitted metrics] → Keep the default-All selection valid when the query returns no values and document panel no-data behavior; do not fabricate selector options.
- [Grafana panel JSON and value-mapping details are version-sensitive] → Use the Grafana version already pinned by the project and cover the provisioned JSON contract without adding dependencies.
- [A broad health panel could hide which service failed] → Keep a separately titled status panel for each monitored target/component and preserve target-specific labels.
- [The two provisioned dashboards can drift if generated output is edited directly] → Treat the base dashboard plus derivation script as authoritative and retain the equality test.

## Migration Plan

1. Add/update static contract tests first for selector labels/defaults, separated panels, health mappings, counter panels, and shared dashboard parity.
2. Update the base dashboard queries, variables, sections, panel types, sizing, and health panels; update the derivation script's outcome panels to use the specified count visualization, then regenerate the improved dashboard.
3. Run focused monitoring tests, the dashboard derivation check, and the full Python test suite. Inspect the provisioned dashboard in Grafana only when the user authorizes Docker commands; no destructive reset is needed.
4. Roll back by restoring the previous dashboard JSON, derivation output, and matching tests. Leave Prometheus exporters, Kafka topics, PostgreSQL rows, and named volumes intact.
